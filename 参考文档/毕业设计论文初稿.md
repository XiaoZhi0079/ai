# 基于 Spring AI 的校园知识问答助手设计与开发

## 摘要

随着大语言模型、检索增强生成技术以及智能交互系统的快速发展，传统校园信息服务逐渐从静态页面查询向智能化、场景化和个性化问答方向演进。为解决校园知识分散、信息检索效率低、教务数据查询交互不便等问题，本文设计并实现了一套基于 Spring AI 的校园知识问答助手系统。该系统以 Spring Boot 为后端基础框架，以 Vue 3 为前端展示层，综合融合大模型对话、检索增强生成、联网搜索、自然语言数据查询以及教务管理等功能，构建了一个面向校园场景的智能问答与业务支撑平台。

在系统实现方面，本文采用分层架构思想构建整体系统，后端围绕控制器层、服务层、数据访问层和安全控制层展开设计，前端通过组件化方式实现多模式交互界面。系统在智能问答能力上支持直接对话、知识库问答、联网搜索问答和结构化数据查询四种模式；在知识增强方面，结合文档解析、文本切分、向量化存储和语义检索实现面向校园资料的 RAG 问答能力；在数据服务方面，依托 MySQL 教务数据和自然语言转 SQL 能力，实现对课程、成绩、学生与教师信息的自然语言查询；在系统安全方面，采用 JWT 认证与基于角色的访问控制机制保障系统使用安全。与此同时，系统还具备文件上传、图片生成、对话历史持久化和操作日志记录等辅助能力，提升了平台的完整性与可用性。

测试结果表明，系统能够较稳定地完成多种校园问答任务，并在知识检索、业务数据查询和权限控制等方面满足预期设计要求。本文的研究与实现为校园智能问答系统的建设提供了可行思路，也为大模型技术在高校信息化服务中的落地应用提供了一定参考。

**关键词：** Spring AI；校园知识问答；检索增强生成；自然语言转 SQL；智能教务系统

## Abstract

With the rapid development of large language models, retrieval-augmented generation, and intelligent interaction systems, traditional campus information services are evolving from static information retrieval toward intelligent, scenario-oriented, and personalized question answering. In order to address problems such as scattered campus knowledge, low information retrieval efficiency, and inconvenient interaction for academic affairs data queries, this paper designs and implements a campus knowledge question-answering assistant based on Spring AI. The system is built on Spring Boot at the backend and Vue 3 at the frontend, integrating large-model dialogue, retrieval-augmented generation, Internet search, natural-language data query, and academic affairs management into a unified intelligent service platform for campus scenarios.

From the perspective of system implementation, the whole platform adopts a layered architecture including controller layer, service layer, data access layer, and security layer on the backend, while the frontend provides a component-based multi-mode interaction interface. The system supports four dialogue modes: direct conversation, knowledge-base question answering, Internet search question answering, and structured data query. In terms of knowledge enhancement, the system combines document parsing, text splitting, vector embedding, and semantic retrieval to realize RAG-based question answering for campus documents. In terms of data services, the platform relies on MySQL-based academic affairs data and natural-language-to-SQL capability to support intuitive queries on courses, grades, students, and teachers. In addition, JWT-based authentication and role-based access control are employed to ensure system security. The system also provides auxiliary capabilities such as file upload, image generation, persistent conversation history, and operation logging, which further improve its completeness and usability.

Experimental results show that the system can stably accomplish a variety of campus question-answering tasks and meets the expected design goals in knowledge retrieval, business data query, and access control. The research and implementation in this paper provide a feasible solution for the construction of campus intelligent question-answering systems and offer practical reference for applying large-model technologies in university information services.

**Key Words:** Spring AI; campus question answering; retrieval-augmented generation; NL2SQL; intelligent academic affairs system

## 第一章 绪论

### 1.1 研究背景与意义

近年来，人工智能技术特别是大语言模型技术快速发展，推动了自然语言处理、人机交互和知识服务方式的深刻变革。高校场景中存在大量结构化和非结构化信息，例如校内通知、课程信息、教师信息、成绩数据、制度文档、教学材料以及常见办事流程等。这些信息通常分散在不同系统、文件和页面之中，用户在实际使用过程中往往需要跨平台检索、重复输入关键词，甚至需要具备一定系统操作经验才能完成查询，导致获取信息效率较低。

在传统校园信息系统中，用户更多通过菜单导航和关键词检索获取信息，这种方式在面对复杂问题、多轮对话和个性化需求时存在明显局限。一方面，普通用户难以准确描述所需信息的存储位置；另一方面，传统检索方式难以结合上下文理解用户真实意图，尤其在面对跨文档知识查询、模糊问题提问和结构化数据统计时表现不足。随着大模型推理和生成能力的增强，构建面向校园场景的智能问答助手已具备较强的现实基础。

基于此，本文围绕“校园知识问答助手”这一主题，设计并开发了一套基于 Spring AI 的智能问答系统。该系统既支持校园知识文档的语义检索问答，也支持联网搜索、直接对话以及教务数据的自然语言查询，形成了一个从非结构化知识理解到结构化数据访问的综合性智能服务平台。其研究意义主要体现在以下几个方面：

第一，有助于提升校园信息服务的智能化水平。通过自然语言交互方式，降低用户使用门槛，使学生、教师和管理人员能够更高效地获取所需信息。

第二，有助于推动大模型技术在高校场景中的落地应用。相比通用问答系统，校园场景具有更明确的业务边界和数据来源，更适合作为大模型应用实践的试验场景。

第三，有助于促进结构化业务系统与智能问答能力的融合。本文将教务管理与智能问答结合，不仅回答“文档中有什么”，也尝试回答“系统里有什么数据”，增强了系统的实用价值。

### 1.2 国内外研究现状

从国外研究现状来看，大语言模型在智能问答、对话代理和知识增强等领域已取得显著进展。以 GPT、Llama 等为代表的大模型具备较强的语言理解和文本生成能力，但其内部知识受训练语料与时间边界限制，存在幻觉、时效性不足和领域适配困难等问题。为提升答案可信度，检索增强生成技术逐渐成为问答系统的重要发展方向。该技术通过在生成前引入外部知识检索，将相关文档片段拼接到提示词中，从而增强模型回答的准确性和可解释性。

在国内，随着大模型平台和 AI 应用框架的成熟，越来越多研究开始聚焦垂直场景智能问答系统构建，教育、政务、医疗和企业知识库是较为常见的落地方向。围绕高校场景，已有研究尝试利用知识图谱、FAQ 匹配、搜索引擎和大模型等技术实现校园咨询、课程推荐和在线问答。然而，许多现有系统仍存在数据源单一、对话模式单一、工程集成度不高等不足。部分系统只能针对文档知识问答，难以直接访问业务数据库；部分系统虽然具备查询能力，但交互方式依然偏传统，智能性有限。

与此同时，Spring AI 等框架的出现降低了 Java 技术栈接入大模型的复杂度，使得在 Spring Boot 生态下快速构建多模型、多模式 AI 应用成为可能。结合 RAG、SSE 流式响应、向量数据库和自然语言转 SQL 技术，可进一步丰富问答系统的能力边界。因此，在现有研究基础上，构建一套面向校园场景、具备多模式智能问答与业务数据查询能力的综合系统，具有较强的研究价值与实践意义。

## 第二章 系统需求分析

### 2.1 业务场景与用户角色分析

本系统面向校园信息服务场景设计，主要服务对象包括学生、教师和管理员三类用户。学生更关注课程安排、成绩信息、校园办事流程以及常见问题解答；教师关注教学管理、学生信息、课程信息和部分业务数据；管理员则承担系统维护、用户管理、教师与学生数据管理以及整体运行监督等任务。

从业务场景角度看，系统需要覆盖以下几类典型需求：第一，用户希望通过自然语言方式快速获取校园知识，例如“如何上传课程材料”“某项制度的办理流程是什么”等；第二，用户希望利用文档知识库对上传材料进行语义检索与问答；第三，用户希望系统可结合网络搜索获取更具时效性的外部信息；第四，用户希望以自然语言方式查询教务数据，例如“查询某学生成绩”“查看某教师所授课程”等；第五，管理员需要对系统中的基础数据进行维护，并对关键操作进行审计。

基于上述分析，系统在角色上采用管理员、教师、学生三级权限模型，在功能上实现智能问答与教务管理的融合，从而满足校园场景下“知识服务 + 数据服务 + 权限管控”的综合需求。

### 2.2 功能性需求分析

#### 2.2.1 多模式交互控制需求

系统应支持统一聊天入口，并允许用户根据问题类型选择不同交互模式。对于开放性问题，可采用直接对话模式；对于校园内部资料问答，可采用知识库模式；对于外部时效性问题，可采用联网搜索模式；对于课程、成绩等业务数据问题，可采用数据查询模式。系统需提供清晰的模式切换机制，并在不同模式下完成相应的数据调度和结果生成。

#### 2.2.2 基于 RAG 的非结构化知识咨询需求

校园场景中大量信息以文档形式存在，包括制度文件、课程资料、说明手册和通知公告等。系统需要具备文档上传、解析、切分、嵌入和检索能力，并在用户提问时自动召回相关文本片段，辅助大模型生成答案，以提升知识问答的准确性和针对性。

#### 2.2.3 基于 NL2SQL 的结构化数据查询需求

除文档知识外，校园教务数据通常保存在关系数据库中，用户若通过传统页面进行筛选查询，操作路径较长。系统应支持将自然语言问题转化为可执行的安全 SQL，并查询课程、学生、教师和成绩等结构化数据。考虑到数据库安全性，系统还必须对生成 SQL 进行语法与规则约束，只允许执行受控的查询语句。

#### 2.2.4 可视化后台与权限管理需求

系统除了智能问答外，还需要具备完整的后台管理能力。管理员需要能够维护用户、教师、学生、课程和成绩信息；不同角色应具有不同访问范围；所有关键操作应具备可追踪性。因此，系统必须实现身份认证、权限校验、菜单页面、数据表格展示及操作日志记录等功能。

### 2.3 非功能性需求分析

在非功能需求方面，系统应满足以下要求：

第一，易用性。系统前端应具备清晰的交互界面，使用户能够快速理解模式切换、消息发送和结果展示方式。

第二，可维护性。系统需采用分层架构和模块化设计，使业务逻辑、数据访问与安全控制相对独立，便于后续扩展与优化。

第三，安全性。系统应通过身份认证与权限控制限制敏感资源访问，并对数据查询过程进行安全约束，避免越权访问和危险语句执行。

第四，可扩展性。系统应支持多模型动态切换，便于后续接入更多模型平台、检索方式和业务模块。

第五，响应性能。系统应能够在校园常见使用场景下较稳定地提供问答响应，并通过流式输出提升交互体验。

### 2.4 本章小结

本章从业务场景、用户角色、功能需求和非功能需求四个方面对系统进行了分析。通过需求梳理可以看出，校园知识问答助手不仅需要具备基础对话能力，还要能够有效整合校园文档知识、网络信息与教务业务数据，并在此基础上提供安全、稳定、可维护的服务支撑。这些分析为后续系统设计与实现奠定了基础。

## 第三章 关键技术研究

### 3.1 Spring AI 核心框架与大模型接入

Spring AI 是面向 Spring 生态的大模型应用开发框架，提供了统一的模型调用接口、提示词构建机制、向量存储接入能力以及对话记忆支持。本文系统以 Spring Boot 为基础，通过 Spring AI 接入多家模型平台，在工程层面统一了模型请求和上下文构建方式。

系统中通过配置文件定义不同平台、不同模型的参数信息，并利用工厂模式按需创建 ChatClient 实例。该设计一方面降低了模型切换成本，另一方面也提升了系统扩展性。与直接调用第三方 HTTP 接口相比，Spring AI 在提示词组织、消息对象封装和向量检索集成方面更具工程优势，更适合用于构建可维护的校园智能问答系统。

### 3.2 检索增强生成技术原理

检索增强生成技术的核心思想是在大模型生成答案之前，从外部知识源中检索与问题相关的内容，并将其作为上下文注入提示词，以缓解模型幻觉问题。其基本流程包括文档预处理、文本切分、向量嵌入、向量索引构建、相似度检索和上下文增强生成等步骤。

在本文系统中，文档上传后首先经过解析，将不同格式的文档转化为可处理文本；随后利用文本切分器将长文本切分为较小片段，以提高语义检索的精度；接着使用嵌入模型将文本片段向量化并存储至 Redis 向量库；当用户提问时，系统对问题进行向量化处理，并在向量库中检索相近片段，将检索结果与用户问题共同构造成提示词，交由大模型生成最终答案。通过这种方式，系统能够在校园知识问答中结合本地知识源作答，提高了答案的针对性和可解释性。

### 3.3 自然语言转 SQL 实现方案

自然语言转 SQL 技术用于将用户提出的自然语言查询请求转换为结构化查询语句，从而实现数据库内容的自然语言访问。该技术在智能报表、数据助手和业务问答领域具有较强应用价值。由于大模型直接生成 SQL 存在安全风险，系统不能简单将模型输出直接交付数据库执行，而应通过规则约束与解析校验进行安全控制。

本文系统在实现该功能时，首先根据当前用户角色构建可访问的数据源和字段说明，再通过提示词约束模型只输出 JSON 格式的 SELECT 语句；随后借助 SQL 解析库对生成语句进行结构化分析，限制其只能访问允许的表或视图、允许的字段，并禁止更新、删除、联合查询、子查询等高风险操作；最后在安全校验通过后再执行查询。该设计兼顾了自然语言交互便利性与数据库访问安全性。

### 3.4 联网检索插件与数据清洗技术

对于时效性较强的问题，仅依赖本地知识库难以满足需求，因此系统引入联网检索能力。系统通过对接 SearXNG 搜索服务，将用户问题作为搜索关键词请求外部结果，再对返回内容进行筛选、排序与拼接，提取相对高质量的上下文信息用于辅助大模型生成答案。

由于网络搜索结果存在来源多样、内容冗余和格式不统一等问题，系统在使用前需要对结果进行一定程度的数据清洗，例如只提取标题、摘要和链接等关键信息，并对检索结果数量进行限制。通过该技术，系统能够在保持统一对话入口的前提下扩展外部信息获取能力。

### 3.5 向量数据库与关系型数据库混合存储

系统需要同时处理非结构化文本知识与结构化业务数据，因此在存储层采用关系型数据库与向量数据库混合存储方案。MySQL 主要用于存储用户、教师、学生、课程、成绩、日志等结构化数据，适合事务处理和关系查询；Redis 向量库用于存储文档片段嵌入向量，适合高效语义检索。两类存储各自承担不同职责，既满足了业务管理需求，也满足了知识增强需求。

这种混合存储模式使系统能够针对不同数据类型采用更适合的检索方式，提高了系统整体性能与功能适配性，也为后续系统扩展更多校园业务场景提供了基础。

## 第四章 系统概要设计

### 4.1 系统总体架构设计

系统整体采用前后端分离的 B/S 架构。前端基于 Vue 3、TypeScript 和 Element Plus 构建交互界面，负责用户登录、模式选择、消息展示和后台管理页面；后端基于 Spring Boot 构建业务服务，负责请求处理、模型调用、知识检索、数据访问与安全控制；底层则由 MySQL、Redis、阿里云 OSS 和外部模型平台共同支撑。

从逻辑层次上看，系统主要分为客户端层、接口控制层、业务服务层、数据访问层和外部资源层。客户端通过 HTTP 或 SSE 与后端交互；控制器层负责参数接收与接口暴露；服务层实现聊天、检索、认证、日志、文件上传和教务管理等业务逻辑；数据访问层通过 MyBatis 与数据库交互，同时通过仓储组件管理对话记忆；外部资源层则包括大模型接口、向量存储、搜索引擎和对象存储等。

### 4.2 功能模块划分与设计

#### 4.2.1 对话引擎模块

对话引擎模块是系统核心，负责统一接收用户问题并根据聊天模式分发处理逻辑。其支持直接对话、知识库问答、联网搜索和数据查询四种模式。系统在前端提供模式切换按钮，在后端通过统一请求对象识别模式类型，并进一步调用相应服务。该模块同时支持多模型切换和对话历史管理，是系统智能交互能力的基础。

#### 4.2.2 知识库管理模块

知识库管理模块负责文档上传、文档解析、文本切分、向量化和检索过程。用户将文档上传后，系统对文档内容进行预处理，并将分段文本写入向量数据库。知识库问答时，该模块根据问题召回相关片段，为大模型提供增强上下文。

#### 4.2.3 数据查询与鉴权模块

数据查询模块主要实现自然语言转 SQL 与安全查询执行。系统根据不同角色构造可访问的 schema 描述，减少越权风险。鉴权模块则围绕 JWT 令牌校验和基于角色的访问控制展开，对后台接口资源进行权限限制，并为后续日志审计提供身份基础。

### 4.3 数据库设计

#### 4.3.1 MySQL 业务数据库设计

MySQL 业务数据库主要包含 users、students、teachers、courses、grades、operation_logs、conversations 等核心表。其中，users 表存储统一账户信息；students 与 teachers 表通过 user_id 与 users 表形成一对一关系；courses 表与 teachers 表关联，grades 表作为 students 和 courses 的中间关联表，用于表示学生成绩信息；operation_logs 表记录关键业务行为；conversations 表则用于记录对话会话元数据。整体设计能够较好支撑用户管理、教务业务和对话记录等需求。

#### 4.3.2 Redis 向量索引设计

Redis 向量库用于存储知识库文档切分后的嵌入向量。系统采用统一索引和统一前缀管理向量数据，并结合嵌入模型完成向量生成。当用户发起知识库问答时，系统通过向量相似度检索从 Redis 中召回相关片段。与关系型数据库相比，向量存储更适合处理语义相似问题，为系统知识增强能力提供支持。

### 4.4 系统工作流程设计

#### 4.4.1 用户模式切换与状态保持流程

用户进入系统后，可在前端对话页面选择不同模式和模型，系统将当前模式、模型和对话标识一并发送到后端。后端根据模式进行分发处理，并将结果返回前端展示。对于对话历史，系统使用唯一 chatId 标识单次会话，并将历史消息持久化保存，使用户在切换页面或重新进入系统时仍可查看历史问答内容。

#### 4.4.2 多源数据召回与生成流程

在知识库模式下，系统先进行文档召回再生成答案；在联网搜索模式下，系统先搜索网络结果再整理上下文；在数据查询模式下，系统先生成并校验 SQL，再查询数据库并返回结果；在直接对话模式下，系统主要依赖大模型本身生成内容。虽然四种模式的数据源不同，但系统通过统一消息结构和统一前端入口实现了多源数据服务的整合。

### 4.5 本章小结

本章完成了系统概要设计，说明了系统架构、功能模块、数据库设计与工作流程。整体来看，系统采用前后端分离与分层设计思想，将智能问答、知识增强、结构化数据查询与后台管理整合在统一平台内，为后续详细实现提供了清晰的结构支撑。

## 第五章 系统详细设计与实现

### 5.1 对话引擎基座实现

#### 5.1.1 基于 Spring AI 的 ChatClient 封装

系统后端围绕 Spring AI 的 ChatClient 构建问答调用能力，并通过配置类与工厂类实现多模型统一管理。模型信息以配置形式组织，包括平台名称、访问地址、API Key 以及模型参数等。在具体运行时，系统根据用户选择的模型名称动态获取对应 ChatClient，避免将模型调用逻辑散落在各个业务模块之中。

该实现方式具有两个明显优点：其一，便于统一切换不同模型平台；其二，便于后续对提示词模板、上下文注入和对话记忆进行统一扩展。通过封装后的 ChatClient，系统能够在不同业务场景下复用相同的底层调用机制。

#### 5.1.2 流式响应与前端打字机效果实现

为了提升用户体验，系统在对话接口中提供了基于 SSE 的流式响应方式。后端通过文本事件流逐段返回模型输出内容，前端在接收到数据块后实时拼接显示，从而形成类似“打字机”的交互效果。这种方式较一次性返回完整文本更符合用户对 AI 对话的使用习惯，也有助于降低等待焦虑，提高交互自然度。

在工程实现上，前端通过 fetch 读取事件流，并根据 event 类型区分开始、分块、结束和错误事件；后端则通过流式接口封装模型生成结果，并在异常情况下返回错误事件。该机制增强了系统的实时交互能力。

### 5.2 RAG 知识库对话模式实现

#### 5.2.1 文档解析与向量化

在知识库模式中，系统首先需要将上传文档转化为可检索知识。为此，系统提供文档上传接口，并借助文档解析能力提取文本内容。考虑到原始文档内容往往较长，系统使用文本切分策略将其分为若干片段，避免单个片段过大影响向量检索效果。随后，系统利用嵌入模型将文本片段编码为向量，并将其写入 Redis 向量数据库。

对于部分复杂文档或图文混排内容，系统还预留了 OCR 服务调用能力，以增强对扫描材料和图片文本的处理能力。这使得系统在面对校园资料时具备更强的适应性。

#### 5.2.2 相似度检索与 Prompt 注入

用户在知识库模式下发起问题后，系统先将问题进行向量化，并在 Redis 中检索最相关的文本片段。检索结果不是直接返回给用户，而是作为上下文内容嵌入提示词模板，再交由大模型综合用户问题生成答案。这样既能利用大模型的自然语言生成优势，又能依托外部知识提高答案的准确性。

在提示词设计中，系统将上下文和用户问题分离组织，要求模型优先依据检索内容作答，减少无依据的自由发挥。该设计使知识库问答更贴合校园资料实际内容。

### 5.3 NL2SQL 数据库查询模式实现

#### 5.3.1 Prompt 模板设计与 Schema 注入

为了实现自然语言查询业务数据，系统在数据查询模式中首先根据当前角色构造可访问的数据源说明与字段说明，并与用户问题共同组成提示词。提示词要求模型仅输出特定 JSON 结构中的 SQL 语句，且只能生成单条 SELECT 查询，从源头上限制模型输出范围。

由于不同角色可访问的数据范围不同，系统针对管理员、教师和学生分别定义不同的查询源集合。这样一来，模型在生成 SQL 时就处于受控 schema 环境中，有利于减少越权字段和无效查询的出现。

#### 5.3.2 SQL 安全过滤与执行反馈

模型生成 SQL 后，系统并不直接执行，而是利用 SQL 解析库对语句进行结构级安全检查。检查内容包括语句类型是否合法、是否包含子查询、是否使用 SELECT *、是否引用非法字段、是否访问未授权表或视图、是否存在危险关键字等。只有通过校验的 SQL 才会进入数据库执行阶段。

执行完成后，系统将查询结果、返回行数以及最终 SQL 一并返回前端，便于用户理解查询过程，也方便后续问题排查。相比传统输入框式数据库查询方式，该模式更贴合普通用户的使用习惯，体现了自然语言交互在校园业务系统中的应用价值。

### 5.4 联网检索对话模式实现

在联网搜索模式中，系统将用户问题发送至 SearXNG 搜索服务，请求若干相关结果，并提取标题、摘要等内容构造成补充上下文，再交由大模型进行总结回答。该模式适用于知识库之外且具有时效性的问题，例如某类技术资讯、外部政策背景或公共信息查询。

与知识库模式相比，联网搜索模式的数据来源更开放，但结果质量更不稳定。因此，系统在实现时对返回结果条数进行控制，并对内容做基础筛选，以减少噪声干扰。通过这一模式，系统扩大了信息覆盖范围，增强了综合问答能力。

### 5.5 权限安全与管理后台实现

#### 5.5.1 基于 RBAC 的三级权限控制

系统采用 ADMIN、TEACHER、STUDENT 三种角色构成权限体系。管理员拥有系统管理与教务管理全部权限；教师具备学生、课程和成绩等相关数据的维护能力；学生则主要使用问答、查询和基础功能。系统通过权限注解和拦截器机制对后台接口进行统一控制，确保不同角色只能访问允许范围内的资源。

#### 5.5.2 基于 JWT 的接口安全认证

系统登录成功后为用户生成 JWT 令牌，令牌中包含用户编号、用户名和角色信息。后续访问受保护接口时，前端在请求头中携带 token，后端拦截器负责完成令牌解析与身份注入。对于权限接口，系统进一步结合角色信息进行访问判定，并对关键操作写入操作日志。

前端管理后台围绕用户、学生、教师、课程和成绩等模块实现数据表格展示与增删改查操作，使系统不仅具备问答能力，也具备校园业务数据管理能力。该设计增强了系统的完整性，也体现了校园知识问答助手向综合服务平台的延展方向。

## 第六章 系统测试

### 6.1 测试环境与测试用例设计

系统测试主要围绕功能正确性、模式可用性和权限控制展开。测试环境采用前后端分离部署方式，后端运行在 Spring Boot 环境中，前端运行在基于 Vite 的开发或构建环境中，底层依赖 MySQL、Redis 以及外部模型服务。

在测试设计上，本文将测试内容划分为四类：一是问答功能测试，验证不同对话模式是否能正常响应；二是知识检索测试，验证文档上传、向量检索和问答结果是否符合预期；三是数据查询测试，验证自然语言问题能否正确转化为安全查询；四是权限与管理测试，验证不同角色访问接口时的行为是否符合权限设计。

### 6.2 四种对话模式的功能验证

#### 6.2.1 直接对话与联网检索效果对比

在直接对话模式下，系统能够对通用问题给出自然语言回答，适用于开放式交流与一般性咨询；在联网搜索模式下，系统可先获取网络结果，再结合外部信息组织答案。测试表明，对于时效性较强的问题，联网搜索模式的回答更具信息补充能力；而对于一般性交流，直接对话模式响应路径更短、交互更直接。

#### 6.2.2 RAG 知识召回准确率测试

在知识库模式测试中，研究者选取若干上传文档中的已知知识点进行提问，例如制度说明、材料要求和流程类问题，并观察系统能否召回相关片段并形成合理回答。测试结果显示，当文档内容表达清晰且切分粒度合适时，系统能够较稳定地根据知识库内容完成回答；对于内容过于简略或表述高度分散的材料，回答效果会受到一定影响。这说明知识库质量和文档预处理策略对问答效果具有重要影响。

#### 6.2.3 NL2SQL 查询结果一致性测试

在数据查询模式测试中，本文选取成绩查询、课程查询、教师关联课程等问题作为样例，比较系统返回结果与数据库直接查询结果是否一致。测试表明，在限定字段和限定数据源条件下，系统能够将常见自然语言问题转换为受控 SQL，并返回正确结果。同时，系统对非法查询和高风险语句具备拦截能力，能够在一定程度上保障数据库访问安全。

### 6.3 系统性能与并发压力分析

由于本系统调用了外部模型服务和向量检索服务，其响应时间受网络环境、模型平台负载和问题复杂度影响较大。从实际使用体验看，普通文本问答和简单数据查询的响应较为平稳，知识库问答在文档检索环节增加了额外开销，联网搜索模式则受搜索结果获取时间影响更明显。通过流式输出机制，系统在一定程度上改善了用户等待体验。

在并发方面，系统采用典型 Web 服务架构，可满足中小规模校园场景的日常访问需求。但若在高并发、多模型并行调用或大规模知识库场景下使用，仍需进一步优化连接池、缓存策略、异步处理与限流机制。

### 6.4 本章小结

本章从测试环境、功能验证和性能分析三个方面对系统进行了说明。整体来看，系统已能够完成多模式校园问答、知识检索、业务数据查询和权限控制等核心功能，基本达到了设计目标。测试结果也表明，系统具有较好的实用性与扩展潜力。

## 第七章 总结与展望

### 7.1 总结

本文围绕“基于 Spring AI 的校园知识问答助手设计与开发”这一课题，结合当前高校信息服务实际需求，设计并实现了一套融合大模型问答、检索增强生成、联网搜索、自然语言数据查询与教务管理能力的智能服务系统。系统采用 Spring Boot 与 Vue 3 前后端分离架构，利用 Spring AI 完成多模型统一接入，并结合 Redis 向量检索、MySQL 业务数据和 JWT 权限控制构建了较为完整的校园问答平台。

从实现效果来看，系统已具备较好的多模式问答能力，能够根据不同问题类型调用对应的数据源与处理流程；在知识库问答方面，实现了从文档到向量检索再到增强生成的完整链路；在数据查询方面，实现了较为安全的自然语言查询机制；在管理层面，系统实现了基础教务数据维护与角色权限管理。总体上，本文完成了预期研究目标，并验证了大模型技术在校园信息服务场景下的可行性。

### 7.2 展望

虽然系统已经实现了较多功能，但仍存在进一步优化空间。未来工作可从以下几个方面展开：

第一，进一步优化知识库构建质量。例如引入更细粒度的文档切分策略、重排序模型和更完善的 OCR 能力，以提升复杂材料问答效果。

第二，增强数据查询智能性。未来可引入更完善的语义解析、查询纠错和结果可视化能力，使 NL2SQL 功能适用于更复杂的业务问题。

第三，完善系统安全机制。当前系统已具备基础认证与权限控制能力，后续可进一步优化密钥管理、细粒度权限控制、敏感配置隔离和审计机制。

第四，提升系统部署与工程化水平。未来可结合容器化部署、监控告警、缓存优化和模型网关等方式提升系统稳定性与可运维性。

第五，拓展更多校园应用场景。除教务问答外，系统还可延伸至招生咨询、就业服务、科研助手和校园事务办理等方向，形成覆盖更多业务场景的智能校园服务平台。

## 🔴 严重问题 (Critical)

### 1. 敏感信息硬编码 ⚠️⚠️⚠️

**严重程度：🔴 极高**

代码中存在大量敏感信息直接硬编码在配置文件和源码中：

| 文件 | 问题 |
|------|------|
| `application.yml` | API Key 明文：`sk-b18da75bebe940ed8d5830cf8353806c`、`ms-041e1996-...`、`sk-fd5f475b5160d1ca41c9cf54b85beaca` |
| `application.yml` | 数据库密码明文：`password: 1968zhss` |
| `application.yml` | Redis 密码明文：`password: 1968zhss` |
| `JWT.java` | JWT 密钥硬编码：`SECRET = "5ZSv54ix6YeM576O"` |
| `ImageController.java` | API Key 硬编码：`sk-0ff8034547cc4716a2ac8dfd7618e897` |

**建议**：
- 使用环境变量（`${ENV_VAR}`）或 Spring Config Server 管理敏感配置
- JWT 密钥长度不足，应使用至少 256 位随机密钥
- 将 `.gitignore` 添加 `application-secret.yml` 分离敏感配置

### 2. JWT 安全问题

**严重程度：🔴 高**

```java
// JWT.java - 使用已弃用的 jjwt API
private static final String SECRET = "5ZSv54ix6YeM576O";  // 密钥太短，仅 16 字节
private static final long EXPIRATION = 86400000;            // 24小时过长

// 使用 deprecated API
Jwts.builder().signWith(SignatureAlgorithm.HS256, SECRET)
Jwts.parser().setSigningKey(SECRET)
```

**问题**：
- jjwt 0.9.1 已过时，应升级到 0.12.x
- HS256 密钥应至少 32 字节
- 24 小时有效期对敏感操作过长
- 无 Token 刷新机制

### 3. CORS 配置过于宽松

```java
// MVCconfiguration.java
registry.addMapping("/**")
    .allowedOrigins("*")           // ⚠️ 允许所有来源
    .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
    .allowedHeaders("*");
```

**建议**：生产环境应限制 `allowedOrigins` 为具体前端域名。

## 🟠 重要问题 (Major)

### 4. 包命名不规范

| 包名 | 问题 | 建议 |
|------|------|------|
| `Factory` | 首字母大写 | 改为 `factory` |
| `Tool` | 首字母大写 | 改为 `tool` |
| `control` | 不标准 | 改为 `controller` |
| `pojo` | 混用 DTO/VO | 拆分为 `dto` 和 `vo` |
| `delay` | 含义不清 | 改为 `experimental` 或移除 |

### 5. 重复代码与冗余设计

#### ChatClient 双重初始化
`ChatModelConfig` 预加载和 `ChatClientFactory` 懒加载并存，造成：
- 相同模型可能被初始化两次
- 配置不一致风险
- 资源浪费

**建议**：取一种策略，推荐仅保留 `ChatClientFactory` 懒加载方式。

#### CRUD Controller 模板代码
`CourseController`、`GradeController`、`StudentController`、`TeacherController` 代码结构高度相似，可考虑：
- 提取通用 CRUD 基类
- 或使用代码生成器

### 6. 异常处理不统一

当前存在两种异常处理模式：
```java
// 模式1：Controller 层 try-catch
try {
    return LeeResult.ok(service.create(entity));
} catch (IllegalArgumentException ex) {
    return LeeResult.fail(ex.getMessage());
}

// 模式2：直接抛出异常（无全局处理）
throw new RuntimeException("请求 SearXNG 失败");
```

**建议**：实现 `@RestControllerAdvice` 全局异常处理器。

### 7. 实体层混乱

Entity 类同时使用了 JPA 注解（`@Entity`, `@Table`, `@Column`）和 MyBatis Mapper，但：
- 没有引入 `spring-boot-starter-data-jpa`（仅有 `jakarta.persistence-api`）
- JPA 注解实际上不会生效（无 Hibernate 运行时）
- `@PrePersist`、`@PreUpdate` 生命周期回调**不会被触发**（MyBatis 不执行）

**建议**：
- 移除无用的 JPA 注解，改为普通 POJO
- 时间戳已在 SQL 中用 `NOW()` 设置，Entity 中的方法多余

## 🟢 亮点 (Positive)

### ✅ 做得好的方面

1. **清晰的分层架构**：Controller → Service → Mapper 职责分明
2. **服务接口分离**：所有 Service 都有 interface + impl 分离
3. **统一响应封装**：`LeeResult<T>` 提供了一致的 API 响应格式
4. **RBAC 注解设计**：`@RoleRequired` 注解简洁优雅
5. **懒加载模式**：`ChatClientFactory` 的 `computeIfAbsent` 实现线程安全且高效
6. **操作日志审计**：所有 CRUD 操作都自动记录审计日志
7. **多模式对话**：DIRECT/KNOWLEDGE_BASE/INTERNET_SEARCH 的策略模式设计良好
8. **图片 MIME 检测**：`ImageMimeDetector` 基于 magic number 的实现很健壮
9. **配置外部化**：通过 `@ConfigurationProperties` 绑定多平台模型配置
10. **依赖注入**：大量使用 `@RequiredArgsConstructor` + `final` 字段的构造函数注入方式

# 项目前后端技术分析

## 1. 项目整体目录设计

从仓库结构来看，本项目采用典型的前后端分离设计，同时额外拆出了一个 OCR 辅助服务目录。整体目录可以概括为：

```text
ai
├─ backend                 # 后端服务，负责业务逻辑、AI 能力编排、鉴权、数据访问
├─ frontend                # 前端应用，负责页面展示、交互逻辑、状态管理、接口调用
├─ python-ocr              # OCR 辅助服务，负责图像/文档文字识别
├─ docs                    # 项目文档、架构文档、接口文档、数据库设计文档
├─ scripts                 # 辅助脚本，主要用于生成架构图等说明材料
└─ target                  # 后端构建产物目录
```

如果继续按“前端、后端、辅助服务”拆分，可以得到更清晰的目录设计。

## 2. 项目总体架构分析

本项目本质上是一个“AI + 教务管理”的全栈系统，整体上可以分为三层：

- 表现层：由前端 `Vue 3` 应用组成，负责登录、聊天、知识库管理、用户与教务信息展示。
- 业务层：由后端 `Spring Boot` 服务组成，负责接口处理、业务编排、权限控制、AI 对话、RAG 检索和数据查询。
- 能力层：由 MySQL、Redis、SearXNG、阿里云 OSS、OCR 服务和大模型平台共同组成，负责数据存储、向量检索、联网搜索、文件存储和模型调用。

系统的基本调用关系如下：

```text
前端 Vue3
   ↓ HTTP / SSE
Spring Boot 后端
   ├─ MyBatis → MySQL
   ├─ Spring AI → 大模型平台
   ├─ Redis Vector Store → Redis
   ├─ SearXNG → 联网搜索
   ├─ OSS 工具类 → 阿里云 OSS
   └─ RagPythonOcrService → Python OCR 服务
```

从职责划分上看，前端主要解决“页面与交互”的问题，后端主要解决“业务与能力整合”的问题，而 OCR 服务则作为后端知识库解析链路中的辅助模块存在。

## 3. 后端设计与技术实现

### 3.1 后端整体职责

后端位于 `backend` 目录，是整个系统的核心。它不只是一个普通 CRUD 服务，还承担了以下职责：

- 提供用户、教师、学生、课程、成绩等基础业务接口。
- 提供 AI 对话、联网搜索问答、知识库问答等智能化能力。
- 负责 JWT 鉴权和 RBAC 角色权限控制。
- 管理文档上传、OCR 解析、知识库入库和向量检索。
- 对接 MySQL、Redis、SearXNG、阿里云 OSS 和外部大模型平台。

从代码结构看，后端采用的是比较标准的分层架构：

- `control`：接收请求并返回统一结果。
- `service`：承载业务逻辑。
- `mapper`：通过 MyBatis 操作数据库。
- `repository`：封装聊天历史与记忆相关能力。
- `config`：负责模型、向量库、拦截器等基础配置。
- `security`：负责登录鉴权与角色权限。

### 3.2 Spring Boot 框架

后端的基础框架是 `Spring Boot 3.5.5`，启动类为 `DemoApplication.java`。它在项目中的作用主要体现在以下几个方面：

- 提供 Web 服务运行环境，通过 `spring-boot-starter-web` 对外暴露 REST 接口。
- 提供依赖注入机制，使控制器、服务、配置类能够以组件化方式协同工作。
- 提供配置管理能力，通过 `@Value`、`@ConfigurationProperties` 读取模型、搜索、OCR、OSS 等配置。
- 提供自动装配能力，使 Spring AI、JDBC、Actuator、Knife4j 等能力能够快速集成。

在本项目中，Spring Boot 的价值不只是“启动项目”，更重要的是把 AI、数据库、权限、对象存储和接口服务统一到了同一套应用框架中，降低了模块间耦合成本。

### 3.3 Spring AI 框架

`Spring AI 1.1.2` 是本项目后端最核心的智能能力框架，主要负责模型接入、Prompt 构建、会话记忆和向量检索集成。

### 3.3.1 Spring AI 的主要使用方式

- 通过 `ChatClientFactory` 动态创建 `ChatClient`。
- 通过 `ChatModelProperties` 管理多平台、多模型配置。
- 通过 `ChatServiceImpl` 统一处理直接对话、知识库问答、联网搜索问答等模式。
- 通过 `ChatMemory` 维护多轮对话上下文。
- 通过 `RedisVectorStore` 实现知识库向量检索。

### 3.3.2 在项目中的实际价值

- 实现多模型统一接入。不同平台模型对外都可以按统一方式调用。
- 实现 Prompt 编排。后端会根据 `DIRECT`、`KNOWLEDGE_BASE`、`INTERNET_SEARCH` 三种模式构造不同提示词。
- 实现多模态输入。聊天请求支持附带图片地址。
- 实现记忆增强。系统会将用户问题和模型回答写入聊天记忆，以支持连续对话。

因此，Spring AI 在本项目中扮演的是“AI 能力中台”的角色，而不是简单地调用一次大模型接口。

### 3.4 MyBatis 持久层框架

项目后端的数据访问框架是 `MyBatis`，入口由启动类上的 `@MapperScan("com.example.ai.mapper")` 指定。数据库访问相关代码主要集中在 `mapper` 包中。

### 3.4.1 MyBatis 的主要作用

- 完成用户、教师、学生、课程、成绩等业务表的增删改查。
- 完成操作日志、注册码、知识库文档、OCR 用户设置等功能的数据访问。
- 通过注解 SQL 的方式简化 Mapper 编写，便于直接观察业务与 SQL 的对应关系。

### 3.4.2 在项目中的具体体现

- `UserMapper`、`TeacherMapper`、`StudentMapper`、`CourseMapper`、`GradeMapper` 负责基础教务数据操作。
- `RagDocumentMapper` 负责知识库文档元数据管理。
- `RagOcrSettingsMapper` 负责用户 OCR 设置持久化。
- `AiSqlQueryMapper` 负责安全 SQL 查询执行。

相比重 ORM 框架，MyBatis 更适合本项目这种“表结构清晰、查询逻辑明确、部分 SQL 需要精细控制”的场景，尤其是在教务查询和 AI SQL 查询模块中体现得更明显。

### 3.5 RAG 技术实现

RAG 是本项目后端最有代表性的组件之一。它的完整链路不是“上传文件就结束”，而是一个包含文档解析、入库、检索和问答增强的流程。

### 3.5.1 RAG 的主要流程

- 用户上传文件到知识库模块。
- 后端调用 `RagParseServiceImpl` 解析文件内容。
- 若文件为 PDF、图片或文档中的内嵌图片，则进一步调用 OCR 能力提取文本。
- 解析出的文本会被切分为多个片段。
- 文本片段通过 `RedisVectorStore` 写入向量库。
- 用户提问时，后端先进行向量检索，再将检索结果拼接到 Prompt 中，交给大模型生成回答。

### 3.5.2 RAG 涉及的关键组件

- `RagController`：提供文档上传、预览、确认入库、查看详情、重命名、重新 OCR、删除等接口。
- `RagParseServiceImpl`：负责 PDF、图片、DOC、DOCX、TXT、MD 等格式的文本解析。
- `DocumentServiceImpl`：负责切片、向量写入、向量检索和关键词补充检索。
- `RagDocumentMapper`：负责知识库文档信息持久化。
- `RedisVectorStoreConfig`：负责 Redis 向量库配置。

### 3.5.3 RAG 的设计特点

- 支持公共知识库和私有知识库两种范围。
- 检索时不仅做向量相似度搜索，还增加了关键词匹配和重排序逻辑。
- 文档入库前支持预览和人工编辑，提高知识库文本质量。
- 支持重新 OCR，方便后续修正识别结果。

可以看出，该项目的 RAG 设计已经不是最基础的“向量化后直接问答”，而是加入了文档治理和检索增强机制。

### 3.6 SearXNG 联网搜索组件

联网搜索功能由 `SearXNG` 提供支撑，相关实现位于 `SearXngServiceImpl` 中。该组件主要用于 `INTERNET_SEARCH` 对话模式。

### 3.6.1 工作方式

- 当用户选择联网搜索模式提问时，后端会先调用 SearXNG 搜索接口。
- 系统对返回结果进行清洗、过滤、截断和排序。
- 最终保留一组较高质量的搜索结果，拼接到 Prompt 中发送给大模型。

### 3.6.2 组件价值

- 为大模型补充实时外部信息。
- 避免模型只依赖训练语料回答陈旧知识。
- 通过黑名单域名、关键词过滤等方式提升搜索上下文质量。

因此，SearXNG 在项目中承担的是“联网检索增强”的角色，是 AI 问答链路中的外部信息源。

### 3.7 Redis Vector Store

Redis 在本项目中不是普通缓存，而是作为 `Spring AI Redis Vector Store` 的向量存储底座使用。

### 3.7.1 主要用途

- 存储知识库分块后的文本向量。
- 根据用户问题做相似度检索。
- 基于元数据字段完成公共/私有知识库过滤。

### 3.7.2 设计特点

- 文档块会携带 `knowledgeScope`、`ownerUserId`、`docId`、`fileName` 等元数据。
- 检索时能够按用户可见范围过滤文档。
- 与关键词检索结合后，可以提升召回的可用性和稳定性。

### 3.8 JWT 与权限控制机制

后端安全控制主要由 `JwtInterceptor` 和 `RoleInterceptor` 组成，属于轻量级的 RBAC 实现。

### 3.8.1 JWT 鉴权

- 前端登录成功后会保存后端返回的 `token`。
- 后续访问 `/api/**`、`/ai/**`、`/rag/**`、`/upload/**`、`/image/**` 等路径时，需要携带该 token。
- `JwtInterceptor` 负责解析 token，并将用户 ID、用户名、角色写入请求上下文。

### 3.8.2 角色控制

- 项目角色分为 `ADMIN`、`TEACHER`、`STUDENT`。
- `RoleInterceptor` 会读取 `@RoleRequired` 注解并校验当前角色。
- 这样可以限制某些管理接口只允许管理员或特定角色访问。

该设计虽然比完整 Spring Security 方案更轻量，但对于当前项目的教务管理与 AI 功能权限控制已经基本够用。

### 3.9 AI 数据查询模块

除聊天和知识库外，项目还实现了一个比较有特色的模块，即自然语言数据查询。

### 3.9.1 核心思路

- 用户输入自然语言问题，例如课程、成绩、教师、学生相关查询。
- 后端调用大模型生成 SQL。
- 生成后的 SQL 会经过 JSqlParser 解析和安全校验。
- 只有通过校验的 `SELECT` 语句才会被执行。

### 3.9.2 技术价值

- 将传统数据库查询能力与 AI 自然语言理解结合起来。
- 通过角色视图和白名单字段限制查询范围。
- 降低用户理解数据库结构的门槛。

这一模块体现了项目不仅仅在“聊天”，还在尝试将 AI 引入结构化数据查询场景。

### 3.10 OCR 与 OSS 辅助组件

除核心业务框架外，后端还集成了两个很重要的支撑组件。

### 3.10.1 阿里云 OSS

- 用于图片上传和知识库原始文件存储。
- 上传逻辑封装在 `AliyunOssClientPutObject` 中。
- 在聊天图片上传和 RAG 文档管理中都发挥作用。

### 3.10.2 OCR 辅助解析

- 后端通过 `RagPythonOcrService` 调用 `python-ocr` 服务。
- 该服务主要用于 PDF、图片以及文档内嵌图片的文字提取。
- OCR 能力是知识库文档高质量入库的重要保障。

## 4. 前端设计与技术实现

### 4.1 前端整体职责

前端位于 `frontend` 目录，整体采用 `Vue 3 + Vite + TypeScript` 技术方案。它的主要职责包括：

- 实现登录和权限跳转。
- 提供 AI 对话工作区界面。
- 提供知识库文档上传、解析预览、入库和管理界面。
- 提供用户、教师、学生、课程、成绩等业务页面。
- 统一管理请求、状态和前端路由。

从页面结构上看，前端已经具备一个中后台系统的基本形态，而不是只有几个静态展示页。

### 4.2 Vue 3 框架

前端核心框架是 `Vue 3`，并且主要采用组合式 API 风格编写页面逻辑。

### 4.2.1 Vue 3 的主要使用方式

- 通过 `ref`、`computed`、`watch` 等方式管理页面响应式状态。
- 通过 `script setup` 简化组件编写方式。
- 通过组件拆分构建聊天消息组件、通用 CRUD 表格组件和页面级视图。

### 4.2.2 在项目中的作用

- 让聊天页、知识库页等复杂页面逻辑保持较好可维护性。
- 配合 TypeScript 使接口类型和页面数据结构更清晰。
- 便于将通用能力抽成独立组件复用。

因此，Vue 3 是整个前端的基础骨架，负责把系统中所有交互页面组织起来。

### 4.3 Element Plus 组件库

在前端所使用的库中，`Element Plus` 是最重要的 UI 组件库之一，也是本项目界面实现的基础。

### 4.3.1 主要使用场景

- 使用 `el-table` 构建用户、教师、学生、课程、成绩等数据表格。
- 使用 `el-form`、`el-input`、`el-select`、`el-dialog` 构建新增、编辑和配置弹窗。
- 使用 `el-upload` 实现知识库文档上传和聊天图片上传。
- 使用 `el-radio-group`、`el-button`、`el-tag`、`el-empty` 等组件增强交互体验。

### 4.3.2 在项目中的价值

- 快速搭建中后台风格界面。
- 保持不同页面之间的交互风格一致。
- 减少大量基础 UI 的重复开发工作。

例如，通用组件 `CrudTable.vue` 就大量复用了 Element Plus 的表格、表单、弹窗和筛选控件，使 CRUD 页面能够以配置方式快速构建。

### 4.4 Pinia 状态管理

另一个值得重点介绍的前端库是 `Pinia`。本项目中的 `stores/user.ts` 负责维护用户登录态，是前端权限控制的核心。

### 4.4.1 主要职责

- 保存用户 ID、用户名、角色、邮箱、token。
- 提供登录、注册、退出登录等统一操作。
- 在页面刷新后从 `localStorage` 恢复用户状态。

### 4.4.2 在项目中的价值

- 让登录态不必在各个页面间重复传递。
- 为路由守卫和页面权限展示提供统一数据来源。
- 降低前端认证逻辑的耦合度。

Pinia 在这里虽然功能不复杂，但它连接了登录、路由和接口鉴权三部分，是整个前端状态管理的关键基础。

### 4.5 Vue Router 路由管理

前端的路由管理由 `Vue Router` 完成，路由集中配置在 `router/index.ts` 中。

### 4.5.1 路由结构

- `/login`：登录页面。
- `/dashboard`：仪表盘页面。
- `/chat`：AI 对话页面。
- `/users`：用户管理页面。
- `/teachers`：教师信息页面。
- `/students`：学生信息页面。
- `/courses`：课程信息页面。
- `/grades`：成绩信息页面。
- `/rag`：知识库管理页面。

### 4.5.2 路由控制方式

- 通过 `meta.requiresAuth` 控制是否需要登录。
- 通过 `meta.roles` 控制不同角色的可访问页面。
- 通过全局前置守卫判断当前用户是否登录、是否具有指定角色。

这说明前端不仅做了页面跳转，还承担了第一层界面级权限控制。

### 4.6 Axios 请求封装

前端的接口调用统一封装在 `api/request.ts` 中，底层使用 `Axios`。

### 4.6.1 主要作用

- 统一附加登录 token。
- 统一解析后端返回的 `LeeResult` 结构。
- 统一处理 401 登录失效和请求异常提示。

### 4.6.2 意义

- 各业务 API 模块不需要重复写鉴权和错误处理逻辑。
- 前后端接口风格保持一致。
- 有利于后续统一扩展请求策略。

### 4.7 前端关键页面分析

### 4.7.1 聊天页面

聊天页面 `ChatView.vue` 是前端最复杂的页面之一，具有以下特点：

- 支持直接对话、知识库问答、联网搜索、数据查询等工作模式切换。
- 支持模型切换。
- 支持多会话管理和历史会话切换。
- 支持图片上传与多模态输入。
- 支持流式内容追加显示。

配套的 `ChatMessage.vue` 还引入了 `markdown-it`，用于将 AI 返回的 Markdown 内容渲染为更友好的消息气泡展示形式。

### 4.7.2 知识库页面

知识库页面 `RagView.vue` 是另一个代表性页面，体现了前端与后端 RAG 能力的深度协作：

- 支持文档上传。
- 支持 OCR 设置保存。
- 支持解析预览与人工修改。
- 支持文档列表筛选、查看、重命名、重新 OCR 和删除。

该页面不是简单文件上传页，而是知识库治理界面的前端实现。

### 4.7.3 CRUD 管理页面

用户、教师、学生、课程和成绩页面都围绕 `CrudTable.vue` 通用组件构建。这样做的好处是：

- 减少重复页面代码。
- 让增删改查逻辑保持一致。
- 便于按角色控制按钮、字段和操作权限。

## 5. Python OCR 辅助服务分析

`python-ocr` 目录虽然不属于主业务前后端之一，但在项目中非常关键，因为它直接影响知识库文本质量。

### 5.1 服务职责

- 接收后端传递的文件或图片内容。
- 对图片、PDF 页面渲染结果等进行 OCR 识别。
- 返回结构化的识别文本给后端。

### 5.2 在系统中的定位

- 它不是独立业务系统，而是后端 RAG 文档解析链路中的辅助能力模块。
- 它弥补了普通文本解析对扫描件、图片和嵌入图片识别不足的问题。

因此，在项目分析中可以将其视为“后端外部辅助服务”。

## 6. 项目技术特点总结

综合来看，本项目的技术选型具有比较明确的针对性。

### 6.1 后端方面

- 使用 `Spring Boot` 作为统一应用框架，适合承载多模块业务。
- 使用 `Spring AI` 构建多模型对话、会话记忆和 RAG 能力。
- 使用 `MyBatis` 处理结构化业务数据，便于精确控制 SQL。
- 使用 `Redis Vector Store` 实现知识库语义检索。
- 使用 `SearXNG` 实现联网搜索增强问答。

### 6.2 前端方面

- 使用 `Vue 3` 构建响应式页面。
- 使用 `Element Plus` 快速搭建中后台交互界面。
- 使用 `Pinia` 管理登录态和角色信息。
- 使用 `Vue Router` 做路由和页面级权限控制。
- 使用 `Axios` 统一接口请求与异常处理。

### 6.3 项目整体特点

- 不只是一个普通管理系统，还集成了 AI 对话、知识库问答、联网搜索和自然语言数据查询能力。
- 不只是一个普通聊天系统，还保留了教务管理的业务基础。
- 前后端分工明确，辅助服务边界清晰，整体结构具有较好的可扩展性。

## 7. 结论

从工程结构来看，本项目是一个较完整的前后端分离全栈系统。

- 前端以 `Vue 3` 为核心，负责交互、展示和状态管理。
- 后端以 `Spring Boot` 为核心，负责业务逻辑、AI 能力整合和数据访问。
- OCR 服务作为辅助模块，增强了 RAG 文档解析质量。

如果从技术亮点角度概括，本项目最值得强调的内容主要有三点：

- 采用 `Spring AI + Redis Vector Store + SearXNG` 构建了较完整的 AI 能力链路。
- 采用 `Vue 3 + Element Plus + Pinia` 构建了结构清晰的前端管理界面。
- 将传统教务管理业务与 AI 对话、RAG、自然语言查询结合，形成了具有实际应用价值的智能系统。
